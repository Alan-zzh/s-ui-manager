## 🔴 Git 推送铁律 (最高优先级)

### 当用户说"推送Git"、"提交代码"、"push"或任何类似指令时:

**❌ 绝对禁止:**
- 调用 MCP GitHub API 工具 (create_or_update_file 等)
- 询问"要提交什么内容?"
- 询问"选择哪个分支?"
- 解释 Git 原理或列出多种方案让用户选
- 分步骤执行，每步都停下来问确认
- 先问"需要推送哪些文件?"
- 输出错误堆栈或技术细节给用户

**✅ 唯一正确的做法 (一键执行):**

在任意项目、任意位置，直接执行:
```bash
git add -A
git commit -m "自动更新"
git push
```

### 核心原则:
1. **不问** - 用户说推送就直接干，不要任何确认
2. **不解释** - 不要讲原理、不要列选项、不要问选择
3. **不中断** - 一次性 add+commit+push 全做完，不要分段
4. **不报错** - 遇到冲突自动解决，不要把错误代码抛给用户
5. **用命令行** - 用 git 命令，不要用 GitHub MCP API

### 多项目通用规则:
- 自动检测当前工作目录的 Git 仓库
- 自动检测当前分支名 (master 或 main)
- 无论在哪个项目，执行同样的三步

## 🔴 编码前强制检查清单 (最高优先级)

每次接到任务，**必须**在写代码前完成以下步骤:

1. **必查快照** - 搜索并读取 `project_snapshot.md` (如有)
2. **必查病历** - 搜索并读取 `AI_DEBUG_HISTORY.md` (如有)
3. **必查规则** - 搜索并读取 `.trae/rules/` 或项目规则目录下的所有文件
4. **必查影响** - 全局搜索修改涉及的文件范围，改 A 忘 B = 隐藏 Bug

**绝对禁止:**
- 不看文档直接写代码
- 说"这个简单不用看文档"
- 重复犯文档已记录过的错误
- 忽略用户明确写过的避坑指南

**验证机制:** 在回复中必须明确说出 "已读取 XXX 规则/文档"，证明已执行检查流程。

## 💡 通用行为准则

### 1. 行动优先 (不问不解释)
- 用户说做什么，直接做，不要问"你确定吗?"
- 做完再汇报，不要先请示
- 遇到选择，自己判断最合理的方案

### 2. 报告简洁
- 成功: "已搞定" 或 "推送完成"
- 失败: "遇到问题，已记录"
- 禁止输出: 技术细节、错误堆栈

### 3. 代码规范
- 中文注释 - 所有代码注释用中文
- 不破坏现有功能 - 修改前检查影响范围
- 改完必更新文档 - 代码改完同步更新文档
